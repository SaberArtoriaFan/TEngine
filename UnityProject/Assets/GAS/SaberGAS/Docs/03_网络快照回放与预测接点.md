# 网络快照回放与预测接点

## 1. 设计目标

这层的目标不是实现网络协议，而是提供一个稳定的逻辑宿主，让外部网络层可以接：

- 客户端预测
- 服务端权威
- 状态纠正
- 回放
- 断线重连

## 2. CombatSimulationHost

`CombatSimulationHost` 是逻辑宿主。

它负责：

- 持有当前 `CombatRuntime`
- 持有命令队列
- 持有命令历史
- 持有快照仓库
- 在需要时恢复快照并重建 `CombatRuntime`

## 3. 命令执行模型

输入使用 `CombatInputCommand` 表达。

当前命令包含：

- `AuthorityMode`
- `ScheduledTick`
- `AbilityActivationRequest`

宿主会在对应 Tick：

1. 把命令取出
2. 修正 `RequestTick`
3. 调用 `CombatRuntime.TryActivate`
4. 记录 `CombatCommandResult`
5. 通过 `ICombatReplicator` 回传预测结果

## 4. 快照

`CombatSnapshot` 当前保存：

- `Tick`
- `WorldState`
- `Payload`

其中真正的核心是 `WorldState`，而 `Payload` 主要是为了给后续序列化层留通道。

## 5. 深拷贝边界

当前宿主不自己实现深拷贝，而是依赖：

- `IDeepCloneProvider`

因此：

- 现在可以先跑逻辑结构设计
- 以后接 FastCloner 时不用改 `CombatRuntime`
- 只需要给 `CombatSimulationHost` 提供深拷贝实现

## 6. 恢复与重放

当前支持：

- `CaptureSnapshot()`
- `TryRestoreSnapshot(tick)`
- `RestoreSnapshot(snapshot)`
- `ReplayFrom(tick, captureSnapshotAfterReplay)`

`ReplayFrom` 的流程是：

1. 找到不晚于目标 Tick 的最近快照
2. 恢复该快照
3. 截断之后的命令历史
4. 重新排入历史命令与仍待执行命令
5. 逐 Tick 重放直到命令耗尽

## 7. 适合如何接网络

### 7.1 服务端

推荐把 `CombatSimulationHost` 放在服务端权威逻辑里：

- 收输入
- 排命令
- 推 Tick
- 定期存快照

### 7.2 客户端

推荐客户端保留同结构宿主做本地预测：

- 本地先执行输入
- 收到服务器纠正后 `ReplayFrom`
- 用同一套逻辑重建正确状态

## 8. 当前有意不做的部分

- 具体网络协议
- 网络压缩
- Delta 编码
- 带宽优化
- 传输层重试

这些应该在更外层完成，而不是污染战斗内核。

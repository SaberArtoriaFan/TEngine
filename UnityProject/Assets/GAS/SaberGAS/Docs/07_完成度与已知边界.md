# Saber.GAS 完成度与已知边界

## 1. 当前结论

如果按本轮目标来判断, `Saber.GAS` 已经完成了“独立通用战斗框架逻辑层”的主体交付, 不再只是骨架。

这里的“完成”指的是:

- 已经从旧 `NewBattle` 思路里抽出了独立核心
- 已经具备 RTS / MOBA / 回合制共用的一套能力系统主链路
- 已经把网络同步前置需要的 Tick / 命令 / 快照 / 重放边界搭起来
- 已经把深拷贝与 Json 留在扩展接口, 没有写死进核心

## 2. 已完成的核心能力

当前代码已经具备下面这些闭环:

- 独立程序集 `Saber.GAS`
- 基于 `Herta.FP` 的确定性主数值
- `Actor / Ability / Effect / Attribute / Resource / Tag` 基础领域模型
- `Attempt -> Block -> Impact -> Resolve` 两段式执行链
- `Instant / Cast / Channeled / Passive` 能力生命周期
- 持续效果、叠层、周期效果、净化移除、Tag 授予撤销
- Tick 推进、命令排队、命令历史、快照捕获、快照恢复、回放
- 面向网络层的 prediction / replication 接口边界
- 面向 FastCloner 的深拷贝接口边界

## 3. 为什么可以认为这不是“只做了骨架”

如果只有骨架, 一般只会停在:

- 类型定义
- 空接口
- 几个还没真正串起来的 manager

当前实现已经明显超过这个阶段, 因为它已经把下面这些真正需要联动的逻辑接通了:

- 技能激活前阻断检查
- 目标解析与射程校验
- 技能成本与冷却提交
- 生命周期实例推进
- effect 转 impact
- impact 转实际状态修改
- 持续 effect 的叠层与到期移除
- 快照恢复后的命令重放

也就是说, 现在缺的不是“逻辑主链路”, 而是“如何接入具体项目表现层与资源层”。

## 4. 当前刻意没有做进核心的部分

下面这些目前仍然是留空或只保留接口, 这是刻意为之:

- Json 具体格式与序列化实现
- FastCloner 的具体接线
- Unity Inspector / ScriptableObject 配置工作流
- 具体表现层 cue, 特效, 动画, UI
- 投射物实体、地面区域实体、寻路或碰撞系统适配
- 客户端预测纠错的项目级策略细节
- 旧资产自动迁移器

这些能力不是不重要, 而是它们属于“接入层”或“项目层”, 如果现在写死进核心, 反而会把 `Saber.GAS` 又做回只服务单一项目的框架。

## 5. 验收时建议重点看什么

如果你周一回来想快速判断交付是否达标, 建议重点看四件事:

- `Runtime` 里是否还存在旧 `NewBattle` 运行时依赖
- 主执行链是否确实是 `Attempt -> Block -> Impact -> Resolve`
- 数值层是否仍然坚持 `Herta.FP`, 而不是又混回 `float`
- 网络宿主是否真的支持“恢复快照后重放命令”

如果这四件事都成立, 说明这套框架的核心方向已经站稳了。

## 6. 下一阶段最合理的工作

如果继续往下做, 更合理的顺序应该是:

1. 先补 ScriptableObject / 配置资产 authoring 层
2. 再补表现 cue / 投射物 / 地面区域等项目适配层
3. 然后接入 FastCloner 与实际网络栈
4. 最后做旧战斗资产到新框架的自动迁移工具

这个顺序的核心原因是: 内核已经足够用了, 后续应该优先解决“怎么落地使用”, 而不是继续把核心拆得越来越抽象。

# Saber.GAS 对象池与生命周期管理
## 1. 这份文档解决什么问题

`Saber.GAS` 在大场景、多单位、频繁施法与频繁回滚时，最容易出现的性能问题不是单次计算量，而是：

- 大量运行时状态对象反复创建 / 销毁
- 容器型对象在高频生命周期里不断扩容、回收
- rollback / replay 反复重建命令桶，导致 `List` 垃圾堆积

这次补的对象池不是通用“哪里都池化”，而是只覆盖“生命周期明确、能够可靠 reset、并且确实会高频 churn”的对象。

## 2. 当前已经池化的对象

### 2.1 Runtime 状态对象

- `CombatActorState`
- `ActiveAbilityInstance`
- `ActiveEffect`
- `AbilityTargetData`

其中前 3 个是典型的“容器较多、生命周期可控”的对象：

- `CombatActorState`
  - 持有能力列表、效果列表、能力实例列表、冷却表、Tag 引用计数表
- `ActiveAbilityInstance`
  - 持有锁定目标列表与多个生命周期 Tick
- `ActiveEffect`
  - 持有效果规格与持续时间状态

### 2.2 Host 临时容器

- `List<CombatInputCommand>`

它主要用于：

- `_scheduledCommands` 的每 Tick 命令桶
- rollback / replay 时的临时命令收集缓冲

这部分对 RTS / MOBA 一类高频输入仿真尤其重要，因为命令重排和重放会非常频繁。

## 3. 池由谁管理

### 3.1 `CombatRuntimePools`

`CombatRuntime` 内部持有 `CombatRuntimePools`，负责：

- `CombatActorState` 池
- `ActiveAbilityInstance` 池
- `ActiveEffect` 池
- `AbilityTargetData` 池

这意味着：

- 战斗单位的动态接入 / 移除
- 持续效果的附加 / 过期
- 长生命周期技能的开始 / 完成 / 取消

都已经能走统一的回收边界。

### 3.2 `CombatSimulationHost`

`CombatSimulationHost` 额外持有 `CombatListPool<CombatInputCommand>`，负责命令调度与重放缓冲的容器复用。

也就是说，战斗宿主不仅负责：

- 命令执行
- 快照捕获
- 快照恢复
- 回滚重放

同时也负责“一场战斗结束时把外层缓冲彻底 reset”。

## 4. 生命周期是怎么落地的

## 4.1 Actor

推荐通过 `CombatRuntime.AddActor(actorId)` 创建单位，而不是外部直接 `new CombatActorState(...)`。

这样做的原因是：

- `AddActor` 会从池中取出 `CombatActorState`
- 进入世界前会执行 `Initialize(actorId)`
- 如果同 ID 单位已存在，会先走 `RemoveActor`

当单位离场时，调用 `CombatRuntime.RemoveActor(actorId)`：

- 先从 `CombatWorldState` 移除
- 再归还内部 `ActiveAbilityInstance`
- 再归还内部 `ActiveEffect`
- 最后归还 `CombatActorState`

## 4.2 Ability Instance

`ActiveAbilityInstance` 不再直接依赖裸 `new` 作为唯一创建方式。

当前回收点有：

- 技能完成：`CompleteAbilityInstance`
- 技能取消：`CancelAbilityInstance`
- 单位移除 / 战斗关闭：`ReleaseActor` / `Shutdown`

这样可以避免持续施法、被动技能、引导技能在大量开始 / 结束时不断制造 GC。

## 4.3 Active Effect

`ActiveEffect` 的生命周期边界也很明确：

- 效果应用时从池中取得
- 效果过期或被移除时归还
- 单位移除或战斗关闭时统一归还

这里特别重要的是：

- 先移除属性修正
- 再移除 granted tags
- 再从 `actor.ActiveEffects` 中移除
- 最后才归还池

否则就会出现“对象已 reset，但角色身上还挂着引用”的脏状态。

## 4.4 临时 TargetData

`ExecuteAbilityStage` 里不再每次都直接保留新的目标数据对象。

现在的流程是：

1. 从池中取一个 `AbilityTargetData`
2. 用 `ActiveAbilityInstance.PopulateTargetData(...)` 填充
3. 用它做目标解析和 impact 生成
4. 当前阶段执行完后立刻归还

这能减少周期效果、引导技能、被动技能在 Tick 推进时的短命对象分配。

## 4.5 命令桶与 Replay 缓冲

`CombatSimulationHost` 中，`_scheduledCommands` 每个 Tick 对应的 `List<CombatInputCommand>` 已经走池化。

命令列表的归还时机包括：

- `ExecuteCommandsForTick` 执行完成后
- `ReplayFrom` 清空旧调度表时
- `Shutdown` 时

因此 rollback / replay 不再每次都制造一批新的命令桶列表。

## 5. 战斗关闭时如何 reset

当前明确的“整场战斗生命周期结束”入口是：

- `CombatSimulationHost.Shutdown()`

它会做这些事：

1. 清空并归还所有调度命令桶
2. 清空命令历史
3. 如果快照仓库支持 reset，则清空快照
4. 调用 `CombatRuntime.Shutdown()`
5. 让 runtime 归还 actor / effect / ability instance
6. 最后 reset runtime 自己持有的对象池

也就是说，真正的一场战斗结束时，内核和宿主两层都能回到“可重新开始”的干净状态。

## 6. Snapshot Restore 为什么也要回收旧 Runtime

`RestoreSnapshot(snapshot)` 现在会在替换 `_runtime` 之前，先对旧 runtime 执行 `Shutdown()`。

原因很直接：

- rollback 会替换整张权威世界状态
- 旧 runtime 内部可能还持有很多 actor / effect / ability instance 的池中对象
- 如果不先回收，旧世界会在回滚链里残留大量内存引用

因此 snapshot restore 也被视为一次“旧 runtime 关闭，新 runtime 接管”的生命周期切换点。

## 7. 当前刻意没有池化的对象

这部分是有意识的选择，不是漏做：

- `CombatActionAttempt`
- `CombatImpact`
- `CombatImpactOperation`
- `AbilityActivationResult`
- `AbilityExecutionRecord`
- `CombatCommandResult`
- `CombatSnapshot`

原因是这些对象当前会：

- 被返回给外部调用方
- 被放入命令历史
- 被快照或调试链路引用

在没有先把它们改造成“稳定快照对象”之前，直接池化会很容易出现引用悬挂和脏数据复用。

所以当前策略是：

- 先池化生命周期绝对清晰的内部状态对象
- 对外暴露结果对象先保持安全

这是一个偏保守但更稳的选择。

## 8. 如果后面还要继续压 GC，优先级建议

下一步最值得继续做的不是把所有对象都塞进池，而是：

1. 把 `Attempt / Impact / Result` 改造成更稳定的只读结果模型
2. 把外部调试/日志链和内部执行链彻底分离
3. 再考虑让内部执行对象完全池化

这样才能在不破坏可观测性和网络重放安全性的前提下，继续往更低 GC 推进。

## 9. 验收建议

你回来验收时，可以优先看下面几件事：

- 是否存在统一对象池基础设施：`CombatObjectPool<T>`、`CombatListPool<T>`
- 是否存在明确的战斗关闭入口：`CombatSimulationHost.Shutdown()`
- 是否存在 runtime 级别的状态归还入口：`CombatRuntime.Shutdown()`
- actor / effect / ability instance 是否都不是“只创建不归还”
- rollback / restore 是否会先释放旧 runtime 再替换
- 是否仍然没有把 `float` / `double` 引回核心战斗数值层

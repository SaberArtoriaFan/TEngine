# 运行时扩展自动注册与拓展指南

## 这次补全了什么

现在 `Saber.GAS` 不只是 `CustomTriggerAction` 支持源码生成自动注册，以下运行时扩展也统一接入了同一类机制：

- `ICombatActionGate`
- `ICombatImpactMutator`
- `ICombatImpactResolver`
- `ICombatRuleModule`
- `ICombatExtensionCloneHandler`

它们的共同特点是：

- 开发者在任意业务程序集里实现接口
- 源码生成器自动扫描当前程序集
- 生成程序集级扩展注册表
- 程序集加载时自动注册到全局 Hub
- `CombatRuntime` 和 `FastClonerDeepCloneProvider` 自动收集并合并这些扩展

这样做的结果是：

- `Saber.GAS` Core 保持纯骨架，不直接引用业务程序集
- 业务层不需要反复写手工装配代码
- 后续迁移整个框架时，扩展实现也会跟着程序集一起走

## 现在有哪些自动注册入口

### 1. `ICombatActionGate`

用途：

- 在行动尝试正式进入执行前追加阻断逻辑
- 适合做资格限制、模式限制、状态限制

示例：

- `Saber.GAS.RTS/Runtime/Examples/RtsAutoRegisteredExtensions.cs`
  - `RtsCommandLockedActionGate`

### 2. `ICombatImpactMutator`

用途：

- 在 `Impact` 真正 resolve 之前改写其中的操作
- 适合做伤害加深、分流、过滤、标记补充

示例：

- `Saber.GAS.RTS/Runtime/Examples/RtsAutoRegisteredExtensions.cs`
  - `RtsSiegeStructureImpactMutator`

### 3. `ICombatImpactResolver`

用途：

- 处理内建 `ImpactOperation` 之外，或需要项目自定义解释的 operation
- 适合把某些特殊 operation 的解释权下放到业务层

注意：

- 它更偏“operation 解释器”
- 如果只是要在 Trigger 触发后做额外动作，优先考虑 `CustomTriggerAction`

### 4. `ICombatRuleModule`

用途：

- 承接较大块的战斗语义解释
- 适合效果阻断、资源变化改写、运行时状态维护

示例：

- `Saber.GAS/Runtime/Semantics/CombatSemanticModule.cs`

这个模块现在已经可以通过自动注册进入：

- `CombatRuntime`
- `FastClonerDeepCloneProvider`

因此示例不再需要手工 `RuleModules.Add(...)`。

### 5. `ICombatExtensionCloneHandler`

用途：

- 为效果扩展定义和运行时状态提供深拷贝支持
- 适合那些挂在 `EffectDefinition.Extensions` 或 `ActiveEffect.ExtensionStates` 上的自定义状态

示例：

- `CombatSemanticModule` 同时实现了 `ICombatRuleModule` 和 `ICombatExtensionCloneHandler`

### 6. `ICombatCustomTriggerAction`

用途：

- 给 `TriggerActionKind.Custom` 提供精确派发的项目专属动作

它和上面几类的区别是：

- 它不是简单列表合并
- 它需要通过 `CustomActionId` 定位具体动作实现

详细说明见：

- `Assets/ScriptsAssembly/SaberGAS/Docs/15_自定义TriggerAction与源码生成.md`

## 自动注册链路

统一链路如下：

1. 某个程序集实现扩展接口
2. Saber.GAS 的源码生成器扫描这个程序集里的实现类
3. 生成程序集级注册表
4. 生成的 `ModuleInitializer` 在程序集加载时自动注册这个注册表
5. `CombatRuntime` 构造时从 `CombatAssemblyExtensionRegistryHub` 收集：
   - 自动注册扩展
   - `CombatRuntimeOptions` 中手工追加的扩展
6. `FastClonerDeepCloneProvider` 构造时从相同的 Hub 收集：
   - 自动注册的克隆处理器
   - 构造函数里手工追加的处理器

这意味着：

- 自动注册是默认能力
- 手工注入仍然保留，用来处理特殊实例或测试场景

## 开发者以后怎么扩展

### 扩展业务逻辑

如果你是要给项目加新逻辑，优先按下面思路选入口：

- 想阻止某个技能/动作发起：用 `ICombatActionGate`
- 想改写一次伤害或治疗的结果：用 `ICombatImpactMutator`
- 想解释新的 operation：用 `ICombatImpactResolver`
- 想维护较大的战斗语义系统：用 `ICombatRuleModule`
- 想给效果扩展状态接深拷贝：用 `ICombatExtensionCloneHandler`
- 想做 Trigger 触发后的项目专属动作：用 `ICombatCustomTriggerAction`

### 扩展框架自身的新自动注册接口

如果以后 `Saber.GAS` 还要新增一种“应当自动注册”的扩展接口，建议按下面步骤补：

1. 在 Core 中定义新接口
2. 把它加入 `ICombatAssemblyExtensionRegistry`
3. 把它加入 `CompositeCombatAssemblyExtensions`
4. 扩展源码生成器，让它扫描并生成这一类实例列表
5. 如果 `CombatRuntime` 需要消费它，就在 Runtime 构造阶段把组合结果接进去
6. 如果 `FastClonerDeepCloneProvider` 需要消费它，就在对应构造阶段接进去
7. 补 Example 和文档

也就是说，后续如果还要继续扩自动注册体系，主线应该是：

- Core 协议
- 程序集级注册表
- 组合视图
- 运行时接线
- 文档与示例

而不是重新发明一套新的手工装配方式。

## 目前的构造约束

源码生成器当前会收录这类实现：

- `public` 或 `internal`
- 非抽象
- 非泛型
- 具备可直接构造的实例构造函数

这里的“可直接构造”包括：

- 真正的无参构造
- 所有参数都带默认值、因此可以省略参数直接 `new Type()` 的构造

如果某个扩展实现依赖复杂外部依赖注入，那它就不适合走自动注册的默认实例化链路。  
这种情况下，可以继续通过：

- `CombatRuntimeOptions`
- `FastClonerDeepCloneProvider(...)`

手工传入自定义实例。

## 什么时候不要继续堆自动注册

自动注册适合：

- 稳定、可复用、能默认实例化的扩展

不适合：

- 必须依赖场景对象、配置资产或外部容器的实例
- 生命周期必须由宿主显式管理的对象
- 大量一次性临时逻辑

所以不要为了“统一”而强行把一切都做成自动注册。  
能自动注册的，走自动注册；需要宿主控制实例化和生命周期的，仍然保留手工注入。

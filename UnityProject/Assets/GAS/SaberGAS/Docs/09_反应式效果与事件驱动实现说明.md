# 09_反应式效果与事件驱动实现说明

## 1. 先直接回答问题

不是单靠 `Tag` 实现。

在当前这套 `Saber.GAS` 里：

- `Tag` 的职责是“描述状态”和“参与条件判断”
- `EffectDefinition` 的职责是“定义一个效果会给目标带来什么状态、数值和移除行为”
- `CombatEvent / ICombatEventSink` 的职责是“把运行时已经发生的事实向外广播”
- `ICombatActionGate / ICombatImpactMutator / ICombatImpactResolver` 的职责是“把战斗规则扩展回核心结算链”

所以像“被攻击后立刻反击对方”这种玩法，在当前框架里的推荐表达不是：

- 给一个 Buff
- BuffLogic 直接订阅某个事件
- 回调里立刻改战斗状态

而是：

1. 先给目标施加一个 `EffectDefinition`
2. 这个 `EffectDefinition` 通过 `GrantedTags` 给目标打上“可反击”的状态标签
3. 运行时扩展点在 `Impact` 进入或结算时识别这个标签
4. 条件满足后，再生成一次新的 `AbilityActivationRequest`，或者插入一个自定义 `CombatImpactOperation`
5. 最终由 `CombatRuntime` 在同一条确定性时间线上完成反击

一句话概括：

`Tag` 不是触发器，`Tag` 是“触发资格”的标记；真正的触发逻辑要放在运行时扩展点里。

## 2. 为什么旧框架容易写成 BuffLogic 绑事件

你旧框架里的典型写法大概是：

- 给角色挂一个 Buff
- Buff 对应一个 `BuffLogic`
- `BuffLogic` 监听“被攻击”“回合开始”“行动结束”之类的事件
- 一旦事件发生，BuffLogic 在回调里执行额外逻辑

这种设计的优点是直观，写单个玩法很快。

但它的问题也很明显：

- 行为逻辑散在很多 BuffLogic 里，结算链不集中
- 事件先后顺序容易失控
- 很容易把“状态”和“行为”混在一起
- 网络同步时，回调触发顺序、触发时点、回调里是否又派生新事件，都比较难做成严格确定性

你现在做自己的 GAS，设计重心已经不是“单个 Buff 好不好写”，而是：

- 同一个玩法是否能在回合制、RTS、MOBA 中复用
- 触发链能不能被快照、回放、回滚
- 逻辑是否能统一走确定性 Tick
- 行为是否能被 Authoring 数据化

所以这套 `Saber.GAS` 刻意没有回到“每个 Buff 带一个脚本监听器”的结构。

## 3. 当前框架里，几个概念分别负责什么

### 3.1 `EffectDefinition` 负责“效果定义”，不是“行为脚本”

从当前实现看，`EffectDefinition` 主要描述这些内容：

- `GrantedTags`
- `RequiredTargetTags`
- `BlockedTargetTags`
- `RemovedTargetEffectTags`
- `RemovedTargetEffectIds`
- `AttributeModifiers`
- `InstantResourceDeltas`
- `PeriodicResourceDeltas`
- `DurationPolicy`
- `StackPolicy`

也就是说，它擅长表达的是：

- 挂什么状态
- 改什么属性
- 扣/回什么资源
- 周期生效还是瞬时生效
- 同类效果重复施加时怎么叠层
- 进入时顺手把哪些旧效果清掉

但它当前并不负责表达：

- 当角色“被攻击”时触发什么
- 当角色“暴击”时触发什么
- 当角色“血量低于 30%”时触发什么
- 当角色“施法完成”时自动连锁什么

所以看到 `EffectDefinition` 里“只有 Tag”，不代表框架希望“用 Tag 自动触发一切”，而是说明当前版本把 Effect 层收敛成了“状态层”。

### 3.2 `ActiveEffect` 是效果实例，不是逻辑监听器

`ActiveEffect` 当前保存的是运行时实例状态：

- `Spec`
- `StartTick`
- `LastPeriodicTick`
- `ExpireTick`

它负责：

- 记录效果何时开始
- 记录何时触发下一次周期
- 判断是否过期
- 作为属性修正和 Tag 的来源

它并没有实现“订阅某个战斗事件后执行逻辑”的接口。

这也是当前架构的一个明确取向：

- `ActiveEffect` 负责保存状态
- 运行时系统负责扫描状态并做决策

### 3.3 `GameplayTag` 是状态索引，不是事件系统

`GameplayTag` 在这套框架里的主要用途是：

- 标记角色当前处于什么状态
- 作为技能激活的 Required / Blocked 条件
- 作为效果施加的 Required / Blocked 条件
- 作为移除同类效果的筛选条件
- 作为“某个反应逻辑是否有资格触发”的轻量条件标记

例如这些 Tag 都很适合：

- `State.CounterAttack.Ready`
- `State.Stealth`
- `State.Silenced`
- `State.Shielded`
- `Internal.Reaction.CounterAttackRunning`
- `Internal.Reaction.NoReflect`

但 Tag 自己不会做任何事。

Tag 的本质是：

- 可快速查询
- 可复制到快照
- 可参与网络同步
- 可作为条件判断的稳定输入

它不是“脚本回调”。

### 3.4 `CombatEvent` 是对外广播，不是旧 Buff 监听系统的等价替代

当前 `CombatEvent` 只有：

- `Kind`
- `ActorId`
- `Message`

`CombatEventKind` 当前也主要是这些大类：

- `AbilityActivated`
- `AbilityBlocked`
- `AbilityStarted`
- `AbilityCompleted`
- `AbilityCancelled`
- `EffectApplied`
- `EffectExpired`
- `ResourceChanged`
- `TickAdvanced`
- `SnapshotCaptured`
- `SnapshotRestored`
- `ReplayStarted`
- `ReplayCompleted`

这说明它目前更像：

- 日志输出
- UI / 表现层通知
- 回放或调试辅助事件

它并不等价于旧框架里的“完整战斗触发上下文”。

比如你要实现“被敌方近战命中后立刻反击”，只靠当前 `CombatEvent` 是不够的，因为它并不直接告诉你：

- 攻击者是谁
- 防守者是谁
- 是哪一个 `Impact`
- 是伤害前、伤害后，还是效果施加后
- 这次命中是否已经是一次反击链的一部分

所以要非常明确：

当前 `CombatEvent` 可以辅助做外层系统通知，但它不是“旧 BuffLogic 监听体系”的完整平替。

## 4. 当前框架里真正适合承载“反应式玩法”的地方

当前最关键的三个扩展点是：

- `ICombatActionGate`
- `ICombatImpactMutator`
- `ICombatImpactResolver`

### 4.1 `ICombatActionGate`

它适合处理：

- 一个技能能不能释放
- 一个请求是否应当被阻断
- 某些全局规则是否会禁止本次行动

它更像“前置拦截器”。

比如：

- 沉默时禁止释放法术
- 带有某个 Tag 时禁止再次触发连锁反击
- 某个模式下单位在建筑状态中不能释放主动技能

### 4.2 `ICombatImpactMutator`

它适合处理：

- 在 `Impact` 真正 Resolve 前读取和改写它
- 根据攻击方、受击方、当前 Tag、当前 Effect，向 `Impact` 里追加自定义操作
- 改伤害倍率
- 加入反弹、连锁、吸血、护盾吸收之类的派生结算

这是当前最接近“旧事件监听后派生额外结算”的位置。

因为它能同时看到：

- 本次 `CombatActionAttempt`
- 当前 `CombatImpact`
- `Impact` 的来源和目标
- 运行时世界状态

### 4.3 `ICombatImpactResolver`

它适合处理：

- 自定义 `CombatImpactOperation`
- 把 Mutator 添加进去的自定义操作真正执行掉
- 在需要时调用 `runtime.TryActivate(...)` 派生一次新技能

如果说 `Mutator` 是“发现满足条件，需要额外做点事”，那 `Resolver` 就是“真正把这件事做完”。

## 5. “受击反击”在当前框架中的推荐实现方式

## 5.1 核心思路

推荐把“受击反击”拆成三层：

1. `EffectDefinition` 负责把“反击状态”挂到单位身上
2. `GameplayTag` 负责表示“这个状态当前存在”
3. `ImpactMutator + ImpactResolver` 负责在命中发生时，把反击转成一次新的技能激活请求

也就是：

状态归状态，行为归行为。

## 5.2 具体映射关系

旧写法大概是：

| 旧框架概念 | 当前框架里的推荐映射 |
| --- | --- |
| `BuffLogic.Bind(OnAttacked)` | `GrantedTags + ICombatImpactMutator/ICombatImpactResolver` |
| 被攻击事件 | 敌对 `CombatImpact` 命中受击者这一事实 |
| Buff 身上保存逻辑 | `EffectDefinition` 只保存状态；逻辑放在扩展点 |
| 反击执行 | 新建一条 `AbilityActivationRequest` |

## 5.3 一个完整的“受击反击”设计

假设你要实现这个效果：

> 给单位挂一个 Buff。Buff 持续期间，只要它被敌人攻击，就立刻用 `Ability.CounterSlash` 反击攻击者一次。

推荐拆成下面这些资源和逻辑。

### A. Buff 对应的 `EffectDefinition`

这个 Effect 不需要自己“监听事件”，只需要表达：

- 持续时间
- 是否可叠层
- 给目标加什么 Tag

例如：

- `Effect.CounterAttackBuff`
- `DurationPolicy = Timed` 或 `Infinite`
- `GrantedTags += State.CounterAttack.Ready`

如果需要，也可以顺手给一些数值修正：

- 反击期间增加格挡率
- 反击期间增加韧性
- 反击期间禁止再次叠加同类 Buff

### B. 真正执行反击的 `AbilityDefinition`

再定义一个专门的反击技能：

- `Ability.CounterSlash`
- 单体目标
- 目标关系为敌方
- 可能带有近战距离限制
- 内部可以施加伤害、流血、击退等效果

这样做的好处是：

- 反击本身也是能力
- 它能复用现有冷却、目标校验、效果结算链
- 将来网络同步、重放、战报记录都统一

### C. 一个检测“受击触发条件”的 `ICombatImpactMutator`

这个 Mutator 的职责是：

- 扫过每一个即将结算的 `CombatImpact`
- 判断目标单位是否有 `State.CounterAttack.Ready`
- 判断这次 `Impact` 是否来自敌方
- 判断这次 `Impact` 是否属于“应视作攻击”的那一类
- 判断当前不是“反击触发反击”的递归链
- 如果满足条件，向当前 `Impact` 追加一个“触发反击”的自定义操作

### D. 一个执行“触发反击”的 `ICombatImpactResolver`

这个 Resolver 的职责是：

- 识别上一步 Mutator 添加的自定义操作
- 读出“谁是受击者，谁是攻击者，应该触发哪个反击技能”
- 构造一条新的 `AbilityActivationRequest`
- 调用 `runtime.TryActivate(...)`

这样，反击就变成了运行时内部派生出来的一次合法能力释放。

## 5.4 当前版本如何承载“自定义操作”

这里要特别说明一个当前版本的实现边界。

`CombatImpactOperationType` 目前只有：

- `ResourceDelta`
- `ApplyEffect`
- `RemoveEffectsByTag`
- `RemoveEffectById`
- `Cue`

它没有单独的 `Custom` 枚举项。

但 `CombatImpactOperation` 里有：

- `Payload`
- `CueName`

并且 `CombatRuntime` 的处理顺序是：

1. 先跑 `ICombatImpactMutator`
2. 再跑 `TryResolveCustomImpact`
3. 如果没有自定义 Resolver 接管，才走内建 `ResolveBuiltInImpact`

这意味着当前版本虽然没有显式的 `CustomOperationType`，但你仍然可以通过“约定一类 Payload”来做自定义操作。

例如可以约定：

- `Type = Cue`
- `CueName = "Reactive.CounterAttack"`
- `Payload = CounterAttackTriggerPayload`

然后你的 `ICombatImpactResolver` 在 `CanResolve` 里判断：

- `operation.Payload` 是否是 `CounterAttackTriggerPayload`

一旦接管了，它就不会再走内建 `Cue` 处理。

所以：

- 现在就能做
- 但这是一种“当前版本的约定式扩展”
- 如果后面你要把它打磨成自己的正式 GAS，最好补一个显式的 `Custom` 或 `Trigger` 类操作类型

## 5.5 一条推荐的执行链

以“A 打 B，B 身上有反击 Buff”为例：

1. A 释放普通攻击能力
2. `CombatRuntime.TryActivate(...)` 构造 `CombatActionAttempt`
3. 普攻生成一个或多个 `CombatImpact`
4. `ResolveAttemptImpacts(...)` 在真正结算前调用 `ICombatImpactMutator`
5. `CounterAttackMutator` 发现：
   - 当前 `impact.TargetActorId = B`
   - `B.Tags` 里有 `State.CounterAttack.Ready`
   - `impact.SourceActorId = A`
   - A 与 B 为敌对关系
   - 本次普攻不是由“反击系统”派生的二次攻击
6. `CounterAttackMutator` 往本次 `Impact` 里追加一个“触发反击”的自定义 `Operation`
7. `ResolveAttemptImpacts(...)` 进入 `ICombatImpactResolver`
8. `CounterAttackResolver` 接管这条自定义操作
9. `CounterAttackResolver` 生成一条新的 `AbilityActivationRequest`
10. 新请求的 `SourceActorId = B`
11. 新请求的 `AbilityId = Ability.CounterSlash`
12. 新请求的目标是 `A`
13. `runtime.TryActivate(...)` 执行反击
14. 反击技能自己再走完整的 Attempt / Impact / Effect 结算链

这样得到的好处是：

- 反击本身是标准能力
- 它和普通技能一样有日志、有记录、有快照
- 它天然能参与网络同步和回放

## 6. Tag 在这里到底扮演什么角色

可以把 Tag 理解成“战斗状态数据库里的索引键”。

### 6.1 Tag 负责告诉系统“谁有资格触发”

例如：

- `State.CounterAttack.Ready`
- `State.Thorns.Enabled`
- `State.OnHitFreeze.Enabled`
- `State.RevengeMode`

Mutator 在看到 `Impact` 时，先查 Tag。

如果没有这个 Tag，就说明这个单位当前没有对应反应资格，直接跳过。

### 6.2 Tag 负责做防重入和防递归

最容易出问题的就是：

- 反击会不会再次触发反击
- 反弹会不会互相无限弹
- 同一 Tick 里会不会被同一个 AoE 重复触发多次

这时可以用内部 Tag 或内部约定做保护，例如：

- `Internal.Reaction.CounterAttackRunning`
- `Internal.Reaction.NoCounterAttack`
- `Internal.Reaction.TriggeredThisTick`

这些 Tag 不一定给策划看，但非常适合做稳定的运行时限制条件。

### 6.3 Tag 不负责“执行反击”

这一点一定要和旧 BuffLogic 思路区分开。

`State.CounterAttack.Ready` 这个 Tag 只能表示：

- 目标现在带着一个“允许反击”的状态

它不能直接表示：

- 反击技能是哪一个
- 触发时机是前伤害还是后伤害
- 一次命中能触发几次
- 反击要不要消耗这层 Buff
- 反击是否有内置 CD

这些都属于“行为规则”，不属于 Tag 本身。

## 7. 当前版本里，事件系统应该怎么用

## 7.1 可以怎么用

`ICombatEventSink` 当前很适合做这些事：

- 日志
- 调试
- 战斗回放观测
- UI 刷新
- 表现层触发
- 外层系统知道“某个能力已经激活/结束了”

例如：

- `AbilityActivated` 用来播技能条目
- `EffectApplied` 用来飘字或表现 cue
- `EffectExpired` 用来移除图标

## 7.2 不建议直接拿它当战斗权威逻辑入口

原因很简单：

- 当前 `CombatEvent` 信息太薄
- 没有完整的源、目标、能力、效果、阶段、上下文
- 它现在更像“广播消息”，不是“完整触发上下文”

如果你硬要完全照旧思路做：

- Buff 监听 EventSink
- 收到事件后再改战斗状态

那会碰到两个问题：

1. 事件上下文不够
2. 逻辑散到 EventSink 外层，核心结算链会重新变乱

所以当前版本的建议是：

- `EventSink` 用于广播
- 反应式战斗逻辑优先写在 `Mutator / Resolver / Gate`

## 8. 一个更接近 GAS 的推荐拆法

如果你要把它继续打磨成你自己的 GAS，我更推荐把“反应式玩法”拆成三层：

- `GameplayEffect` 风格的状态层
- `Trigger` 风格的反应规则层
- `GameplayAbility` 风格的行为层

在你当前的命名里，就是：

- `EffectDefinition` 负责状态
- `TriggerDefinition` 负责触发条件与触发动作
- `AbilityDefinition` 负责真正执行出来的行为

### 8.1 为什么不建议把行为重新塞回 `EffectDefinition`

如果你把 `EffectDefinition` 重新写成：

- 有状态
- 有数值
- 还能监听所有事件
- 还能主动施法

那它会重新变成旧 BuffLogic 的超级对象。

这样做的问题是：

- 语义太重
- 数据和行为耦合
- 很难重用
- 网络同步时不容易限制触发边界
- 结算顺序会重新分散到很多局部脚本里

更合理的是：

- Effect 只描述“我给了目标什么状态”
- Trigger 只描述“什么情况下因为这个状态而触发额外行为”
- Ability 只描述“真正执行什么行为”

### 8.2 方案 C 的核心目标

方案 C 的目标，不只是把“受击反击”从脚本监听改成数据驱动。

它真正要解决的是：

- 让所有被动、连锁、条件触发、死亡触发、阈值触发都走统一入口
- 让触发逻辑可快照、可回放、可回滚、可预测
- 让同一类机制能同时适配回合制、RTS、MOBA
- 让大部分“Buff 上挂脚本”的玩法回到可配置的结构化数据

如果这一层补完整，未来你很多玩法就不需要再写成：

- `SomeBuffLogic.OnAttacked`
- `SomeBuffLogic.OnDealDamage`
- `SomeBuffLogic.OnTurnStart`

而是写成：

- 一个 `EffectDefinition`
- 一个或多个 `TriggerDefinition`
- 一个或多个 `AbilityDefinition`

### 8.3 Trigger 层应该长什么样

我建议把 Trigger 定义拆成“触发条件”和“触发动作”两部分。

可以理解成：

```text
TriggerDefinition
- Id
- Name
- SourceKind
- EventKind
- Timing
- Priority
- RequiredOwnerTags
- BlockedOwnerTags
- RequiredInstigatorTags
- BlockedInstigatorTags
- RequiredTargetTags
- BlockedTargetTags
- RequiredIncomingAbilityTags
- BlockedIncomingAbilityTags
- RequiredIncomingEffectTags
- BlockedIncomingEffectTags
- RequiredImpactTags
- BlockedImpactTags
- TeamRelationFilter
- TriggerLimitPolicy
- CooldownTicks
- MaxTriggerCountPerTick
- MaxTriggerCountPerWindow
- ConsumeSourceEffectOnTrigger
- RemoveSourceEffectOnTrigger
- DisableWhenSourceDead
- DisableWhenTargetDead
- Action
- CustomPayload
```

这里每个字段的职责建议如下。

`SourceKind` 表示触发器从哪里来：

- `FromEffect`
- `FromAbility`
- `FromActor`
- `FromItem`
- `Global`

`EventKind` 表示由什么事实触发：

- `BeforeAttempt`
- `AfterAttemptSucceeded`
- `AfterAttemptBlocked`
- `BeforeImpactResolve`
- `AfterImpactResolved`
- `BeforeDamageTaken`
- `AfterDamageTaken`
- `AfterDamageDealt`
- `BeforeEffectApplied`
- `AfterEffectApplied`
- `AfterEffectExpired`
- `OnKill`
- `OnDeath`
- `OnAllyDeath`
- `OnResourceThresholdCrossed`
- `OnStateApplied`
- `OnStateRemoved`
- `OnEnterArea`
- `OnLeaveArea`
- `OnTick`

`Timing` 表示动作什么时候落地：

- `ImmediatePreResolve`
- `ImmediatePostResolve`
- `EndOfStage`
- `NextTick`
- `ServerAuthoritativeOnly`

`Priority` 用来解决多个 Trigger 在同一窗口命中时的确定性排序。

`TriggerLimitPolicy / CooldownTicks / MaxTriggerCountPerTick / MaxTriggerCountPerWindow` 用来防止：

- 无限递归
- 多次重复触发
- 同一 AoE 在同一 Tick 里打出多次重复被动

`ConsumeSourceEffectOnTrigger / RemoveSourceEffectOnTrigger` 用来表达：

- 触发一次就消耗护盾
- 触发一次就移除反击姿态
- 触发一次就进入内置冷却

### 8.4 Trigger 动作应该长什么样

触发动作不要只支持“施放一个 Ability”。

如果要做成真正泛用的战斗框架，动作类型至少要覆盖下面这些：

```text
TriggerActionDefinition
- ActivateAbility
- ApplyEffect
- RemoveEffectById
- RemoveEffectsByTag
- AddImpactOperation
- ModifyImpactMagnitude
- AddResource
- RemoveResource
- AddTag
- RemoveTag
- CancelAbility
- CleanseByTag
- EmitCue
- Custom
```

其中最核心的是：

- `ActivateAbility`
- `ApplyEffect`
- `AddImpactOperation`
- `ModifyImpactMagnitude`
- `CleanseByTag`

原因是很多复杂玩法，本质上都能归约成这几类。

例如：

- 受击反击：`ActivateAbility`
- 受击反弹：`AddImpactOperation` 或 `ApplyEffect`
- 暴击后追加斩杀：`ActivateAbility`
- 被控制后净化：`CleanseByTag`
- 低血自动开盾：`ApplyEffect` 或 `ActivateAbility`

### 8.5 还需要一份统一的 Trigger 上下文

如果你要把 Trigger 做成正式系统，就不能再只靠当前 `CombatEvent` 那种极薄的消息体。

你需要一份完整的触发上下文，例如：

```text
CombatTriggerContext
- CurrentTick
- EventKind
- Timing
- OwnerActorId
- InstigatorActorId
- TargetActorId
- RelatedAbilityId
- RelatedEffectId
- RelatedAttempt
- RelatedImpact
- RelatedOperation
- SourceActiveEffect
- SourceAbilityInstance
- Flags
- CustomPayload
```

这份上下文的作用是：

- 让 Trigger 判断条件足够完整
- 让 Trigger 动作拿到足够的数据
- 让后续的快照、回放、调试日志可以追踪“为什么触发”

这里的 `Flags` 我建议至少包含：

- `IsCritical`
- `IsPeriodic`
- `IsReflected`
- `IsTriggered`
- `CanTriggerOtherReactions`
- `BypassesCooldown`
- `WasBlocked`
- `WasImmune`

这样很多细节规则就能变成标准判断，而不是散落在一堆特殊分支里。

### 8.6 Trigger 的运行时实例也需要独立

如果 Trigger 只是定义，没有实例，那么很多常见玩法都不好做。

例如：

- 每 5 秒最多触发一次
- 每层 Buff 各自有独立触发次数
- 这个被动一场战斗只触发 3 次
- 这个反击状态触发后消耗一层

所以我建议补一个运行时实例层：

```text
ActiveTriggerInstance
- Definition
- OwnerActorId
- SourceEffectRef
- SourceAbilityInstanceRef
- LastTriggeredTick
- TriggerCountThisTick
- TriggerCountTotal
- RemainingCharges
- Enabled
```

这层实例可以挂在：

- `ActiveEffect` 上
- `ActiveAbilityInstance` 上
- `CombatActorState` 上
- 世界级规则对象上

也就是说：

- 有些 Trigger 来自一个持续 Buff
- 有些 Trigger 来自一个被动技能
- 有些 Trigger 来自一个英雄固有机制
- 有些 Trigger 来自地图或模式规则

### 8.7 Trigger 应该怎么接进当前运行时

如果按当前 `Saber.GAS` 的实现演进，我建议新增一个统一的 `CombatTriggerProcessor`。

它的职责不要是“监听消息就立即改状态”，而是：

1. 在运行时关键结算窗口收集触发上下文
2. 找出所有可能响应这个上下文的 Trigger 实例
3. 逐个做条件过滤
4. 按确定性规则排序
5. 生成触发动作命令
6. 把这些命令按窗口插回主结算链

一个推荐的执行顺序可以是：

1. `CombatRuntime` 进入某个稳定窗口
2. 构造 `CombatTriggerContext`
3. `CombatTriggerProcessor` 收集候选 Trigger
4. 过滤掉不满足 Tag、阵营、事件类型、CD、次数限制的 Trigger
5. 按 `Priority -> OwnerActorId -> SourceKind -> TriggerId` 排序
6. 逐个执行 TriggerAction
7. 若动作生成新的 Ability 或 Impact，则把它们压入确定性队列
8. 若动作本身会继续触发别的事件，则继续进入下一层窗口
9. 用递归深度限制和 `Flags / InternalTags` 防止死循环

这里最关键的一条原则是：

Trigger 不直接“任意修改世界”，而是把动作重新送回主结算系统。

这样你才能保证：

- 顺序一致
- 网络一致
- 回放一致
- 调试可读

### 8.8 方案 C 下，“受击反击”应该怎么表达

到了方案 C，“受击反击”就不该再主要依赖 `ImpactMutator + Resolver` 的手工约定了，而应该变成完整的三层配置：

`EffectDefinition`

- `Effect.CounterAttackBuff`
- `GrantedTags += State.CounterAttack.Ready`
- `DurationPolicy = Timed`

`TriggerDefinition`

- `Id = Trigger.CounterAttackOnHit`
- `SourceKind = FromEffect`
- `EventKind = AfterImpactResolved`
- `Timing = ImmediatePostResolve`
- `RequiredOwnerTags += State.CounterAttack.Ready`
- `BlockedImpactTags += Internal.Reaction.NoCounter`
- `CooldownTicks = 0` 或一个很短的 Tick CD
- `MaxTriggerCountPerTick = 1`
- `Action = ActivateAbility`
- `TriggeredAbilityId = Ability.CounterSlash`

`AbilityDefinition`

- `Ability.CounterSlash`
- 单体敌方目标
- 可带近战距离校验
- 可施加伤害、流血、打断、击退

这样一来，反击就被拆清楚了：

- Buff 负责“我处于反击姿态”
- Trigger 负责“何时把反击姿态转成一次动作”
- Ability 负责“反击动作做什么”

### 8.9 方案 C 下，文档里提到的那些机制会怎么表达

以下这些例子，放进 `Effect + Trigger + Ability` 之后都会非常自然。

`受击反弹`

- Effect 给目标挂 `State.Thorns.Enabled`
- Trigger 监听 `AfterDamageTaken`
- Action 往攻击者追加一条反伤 `Impact`，或者激活一个反弹 Ability

`暴击后追加斩杀`

- 被动 Ability 或 Effect 挂一个 Trigger
- Trigger 监听 `AfterDamageDealt`
- 过滤条件要求 `Flags.IsCritical = true`
- Action 激活一个 `Ability.ExecuteFollowUp`

`低血量自动开盾`

- Trigger 监听 `OnResourceThresholdCrossed`
- 阈值条件设为生命从大于 30% 跌到小于等于 30%
- Action 施加 `Effect.AutoShield`

`被控制后净化`

- Trigger 监听 `AfterEffectApplied`
- 过滤条件要求来袭效果带 `State.Control.Hard`
- Action 执行 `CleanseByTag(Control.*)` 或激活净化 Ability

`队友死亡后狂暴`

- Trigger 监听 `OnAllyDeath`
- 过滤条件要求队友距离、阵营、英雄类型满足约束
- Action 施加 `Effect.Berserk`

`进入草丛后隐身`

- Trigger 监听 `OnEnterArea`
- Area 或 TerrainQuery 告诉系统当前区域带 `Terrain.Bush`
- Action 施加 `Effect.Stealth`

你会发现，这些玩法的共性其实都一样：

- 先有一个状态或固有规则
- 再有一个被统一识别的触发事件
- 最后把结果转成 Ability / Effect / Impact

## 9. 对“受击反击”这种玩法，当前代码与长期方案怎么取舍

如果你问的是“按当前代码，不改核心结构，最稳的做法是什么”，我的建议仍然是：

### 方案 A：`Tag + ImpactMutator + ImpactResolver`

这是当前最推荐的方案。

优点：

- 完全走核心结算链
- 确定性最好
- 网络同步最容易控制
- 反击是标准能力，后续最好扩展

缺点：

- 需要你自己写一层反应系统实现
- 当前 `CombatImpactOperationType` 没有显式 `Custom`，需要通过 `Payload` 约定

### 方案 B：`Tag + 外层 EventSink + 再次下发 AbilityActivationRequest`

这个方案也能做，但我只建议把它用于：

- UI
- 演出
- 非权威逻辑
- 调试性触发

如果要拿它做核心战斗逻辑，当前信息量偏少，不太推荐。

### 方案 C：长期演进成 `Effect + Trigger + Ability`

这是最适合你“我要做自己的 GAS”这个目标的方向。

它的本质不是多加一层配置，而是把“事件回调式逻辑”收束成统一的、可回放的触发管线。

方案 C 真正补完整之后，至少应当具备下面这些运行时能力：

- Trigger 定义与 Trigger 实例
- 完整的 TriggerContext
- 统一的 TriggerProcessor
- 稳定的触发窗口
- 触发优先级排序
- 触发次数限制与冷却
- 递归防护与防重入机制
- TriggerAction 到 Ability / Effect / Impact 的统一落地

到这一步，框架就不再只是“技能 + Buff”，而是会成为一个真正可承载复杂被动与战斗反应的 GAS。

## 10. 如果把方案 C 和周边底座补全，能不能支撑类似 DOTA 大部分机制

结论先说：

可以支撑到“DOTA 大部分战斗机制程序层”，但不能只靠现在已有的 `Ability + Effect` 两层，还需要把 Trigger 层和几个关键底座一起补完。

更准确地说：

- 如果你的目标是“英雄技能、被动、Buff、Debuff、光环、召唤、净化、控制、反弹、斩杀、死亡连锁、被动禁用、状态抗性、持续伤害、治疗、护盾、幻象规则、物品主动/被动”这一类战斗机制程序
- 那么这套框架在补完后是完全可以承载大部分的

但如果你的目标是“整个 DOTA 世界系统完整复刻”，那还需要更多框架外系统配合，例如：

- 视野与战争迷雾
- 高低地与地形
- 树木、草丛、障碍物
- 路径、碰撞、转身、追击
- 投射物飞行与命中
- 选择、命令、仇恨、AI
- 演出、UI、音频、镜头

所以应当把这个结论理解成：

- 这套框架可以成为 DOTA 风格战斗规则的内核
- 但不会单独覆盖整个 MOBA 世界模拟

### 10.1 现有 `Saber.GAS` 已经具备的基础

现在已经有的部分是：

- 确定性 Tick
- `Actor / Ability / Effect / Tag / Attribute / Resource`
- `Attempt -> Block -> Impact -> Resolve`
- 技能生命周期
- 持续效果与叠层
- 快照、恢复、重放

这些基础非常重要，因为 DOTA 风格战斗里最核心的就是：

- 规则多
- 触发多
- 派生结算多
- 网络一致性要求高

## 10.2 想覆盖 DOTA 类大部分机制，还必须补什么

如果你要冲到“DOTA 大部分机制程序层可表达”，我建议优先补下面这些。

### A. Trigger 系统

这是本章主角。

没有 Trigger，很多被动机制都会重新退化成硬编码监听。

### B. 语义化的 Damage / Heal / Shield 结算模型

当前 `CombatImpactOperation` 还比较轻。

如果要覆盖 DOTA 类技能，建议把伤害与治疗建成正式语义对象，例如：

- `DamageKind`
- `DamageFlags`
- `AttackFlags`
- `HealFlags`
- `CanCrit`
- `CanLifesteal`
- `CanBeBlocked`
- `BypassesShield`
- `BypassesMagicImmune`
- `NonLethal`

这样很多机制才能自然支持：

- 普攻暴击
- 法术吸血
- 伤害格挡
- 伤害免疫
- 反伤不触发吸血
- 神圣伤害、物理伤害、魔法伤害

### C. 更正式的状态与免疫体系

单靠字符串 Tag 虽然能做，但建议再补一层规范化状态语义。

例如：

- `Silence`
- `Mute`
- `Break`
- `Root`
- `Stun`
- `Hex`
- `Disarm`
- `Invisible`
- `MagicImmune`
- `Invulnerable`
- `Untargetable`
- `Phased`

这些状态可以仍然用 Tag 落地，但最好有一层固定约定和查询接口。

这样你才能把：

- 施法限制
- 普攻限制
- 被动禁用
- 目标合法性
- 净化规则

做成统一逻辑，而不是到处手写 Tag 名。

### D. 驱散、净化、状态抗性体系

这是 DOTA 类机制非常核心的一层。

建议显式补：

- `DispelType`
- `ControlStrength`
- `StatusResistancePolicy`
- `ImmunityPolicy`
- `PurgeBehavior`

否则这些常见玩法会很痛苦：

- 强驱散 / 弱驱散
- 只清 Debuff 不清 Buff
- 控制时间缩短
- 魔免下只挡一部分效果
- 某些效果无法净化

### E. Aura / Area / Projectile / Thinker 实体

这部分严格说不该全塞进核心，但必须有正式适配层。

因为很多 DOTA 类技能其实不是“角色自己立刻放一个技能”这么简单，而是：

- 发射一个投射物
- 生成一个地面区域
- 召唤一个 Thinker
- 让光环持续查询附近单位

建议补几类统一运行时实体：

- `ProjectileEntity`
- `AreaEntity`
- `AuraEmitter`
- `ThinkerEntity`
- `SummonedActor`

这些实体本身不一定属于最底层 GAS 核心，但必须和 Trigger / Ability / Effect 严密对接。

### F. 统一 Query 服务

你做 RTS / MOBA 时，很多技能逻辑的关键不是“有无 Tag”，而是“能否准确查询空间与关系”。

至少要有：

- 范围查询
- 锥形查询
- 线段查询
- 最近目标查询
- 阵营关系查询
- 视野可见性查询
- 区域标签查询
- 地形查询

否则很多机制虽然理论可表达，实际很难稳定落地。

### G. 召唤物、幻象、复制规则

这是 DOTA 类机制里比较难但很重要的一层。

如果你以后想支持：

- 幻象
- 分身
- 复制英雄
- 偷技能
- 临时召唤单位

那你需要把“复制哪些状态、屏蔽哪些能力、如何继承 Trigger / Effect”写成正式规则。

这部分和你已经接入的深拷贝、快照机制是能接上的。

## 10.5 一个更接近 DOTA 的建议分层

如果目标真的是做“自己的 GAS，并且能承载 DOTA 类大部分机制”，我建议最后分成下面几层：

1. `Foundation`
   负责确定性 Tick、ID、FixedPoint、随机、基础容器。

2. `Core GAS`
   负责 Actor、Ability、Effect、Tag、Attribute、Resource、Attempt、Impact、Resolve。

3. `Trigger System`
   负责 TriggerDefinition、ActiveTriggerInstance、TriggerContext、TriggerProcessor。

4. `Combat Semantics`
   负责 Damage、Heal、Shield、Dispel、Immunity、StatusResistance、AttackFlags。

5. `Combat Entities`
   负责 Projectile、Area、Aura、Thinker、Summon、Illusion。

6. `World Query Adapters`
   负责阵营、范围、视野、地形、草丛、树木、路径查询。

7. `Presentation / Game Layer`
   负责动画、VFX、UI、音频、镜头、输入、AI。

按这个分法，你的 GAS 内核就不会被 DOTA 的世界系统拖死，但又足以承载绝大多数技能与被动规则。

## 11. 一个实际可执行的建模建议

如果我来给这类玩法做规范，我会要求策划或配置层这样拆：

### Buff / Effect 层

- `Effect.CounterAttackBuff`
- `GrantedTags = State.CounterAttack.Ready`
- `DurationPolicy = Timed`
- `StackPolicy = RefreshDuration`

### Trigger 层

- `Trigger.CounterAttackOnImpact`
- `SourceKind = FromEffect`
- `EventKind = AfterImpactResolved`
- `RequiredOwnerTags = State.CounterAttack.Ready`
- `BlockedImpactTags = Internal.Reaction.NoCounter`
- `Action = ActivateAbility`
- `TriggeredAbilityId = Ability.CounterSlash`

### Ability 层

- `Ability.CounterSlash`
- 单体敌方目标
- 近战距离限制
- 释放后施加伤害 / 击退 / 流血

这样整套链路的职责非常清楚：

- Buff 只负责“我现在可反击”
- Trigger 只负责“什么时候开始反击”
- Ability 只负责“反击时具体做什么”

## 12. 对这份文档的最终结论

最终结论可以压缩成四句话：

1. `EffectDefinition` 里的 `Tag` 不是用来“自动触发逻辑”的，它只是状态与条件标记。
2. 当前框架要做“被攻击后立刻反击”，短期推荐用 `GrantedTags + ICombatImpactMutator + ICombatImpactResolver + AbilityActivationRequest` 来实现。
3. 如果你后面要把这套系统真正进化成自己的 GAS，最关键的补全不是把 Buff 再脚本化，而是新增正式的 `TriggerDefinition / ActiveTriggerInstance / TriggerProcessor`。
4. 在 Trigger、Damage 语义、状态免疫、Aura / Projectile / Area / Query 这些层补完之后，这套框架完全可以承载类似 DOTA 的大部分战斗机制程序，但不应试图单独承包整个 MOBA 世界系统。
